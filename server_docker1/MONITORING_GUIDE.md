# Cloud Security监控平台 · 字段说明

本平台（`http://127.0.0.1:8787`）包含两大监控能力：

1. **GLM 监控**（`/glm-monitor`）—— 实时看 GLM 后端 GPU 的队列/健康，以及各 IP 的调用统计
2. **插件状态**（`/plugin-status`）—— 判断每个员工是否安装并正常使用审计插件

---

## 一、GLM 监控页字段说明

### 1.1 实时队列板块（数据源：vLLM，每 5 秒采样，**实时**）

| 字段 | 含义 | 数据性质 |
|---|---|---|
| **排队中** (waiting) | 此刻已提交给 GPU、但还没轮到开始处理的请求数。大于 0 说明 GPU 忙不过来，新请求要等 | 实时（这一瞬间的值） |
| **处理中** (running) | 此刻 GPU 上正在同时推理的请求数。是 vLLM 连续批处理凑成的一个 batch 里的 seq 数 | 实时（这一瞬间的值） |
| **累计抢占** (preemption) | 从 vLLM 启动至今，累计发生过多少次"抢占"（把正在跑的请求踢出 GPU 腾显存）。只增不减，重启归零 | 累计计数器 |

### 1.2 后端健康板块（数据源：vLLM，每 5 秒采样，实时 + 累计）

| 字段 | 含义 | 数据性质 |
|---|---|---|
| **KV cache 占用率** | 显存里 KV 缓存已用比例。接近 100% 时新请求进不来，是"慢"和"抢占"的直接根因 | 实时 |
| **缓存命中率** | 命中前缀缓存的 prompt token 占比。越高越省算力（重复的对话前缀不用重算） | 累计比值 |
| **累计 prompt** | 从启动至今读入的 prompt token 总量 | 累计计数器 |
| **累计生成** | 从启动至今生成的 token 总量 | 累计计数器 |

### 1.3 各 IP 对话/请求聚合（数据源：LiteLLM，**事后统计**，近 5 分钟窗口）

> ⚠️ 这一整块是**事后统计**——不是"此刻"，而是"过去 5 分钟内**已经完成**的请求"的汇总。

| 字段 | 含义 | 数据性质 |
|---|---|---|
| **使用人** | 由请求的 api_key 反查 LiteLLM key_alias 得到的中文名 | 事后（完成的请求才能反查） |
| **客户端 IP** | 员工机器 IP | 事后 |
| **请求数** | 过去 5 分钟该 IP 发出的 API 调用条数（一个对话会发很多条） | 事后累计（5分钟） |
| **对话数 (session)** | 过去 5 分钟该 IP 开了几个 Claude Code 窗口 | 事后累计（5分钟） |
| **平均耗时** | 该 IP 所有已完请求的平均响应时间 | 事后统计 |
| **最大耗时** | 该 IP 最慢一条请求的耗时 | 事后统计 |
| **失败** | 过去 5 分钟该 IP 失败的请求条数 | 事后累计 |
| **模型** | 调用的模型名（这里只统计 GLM-5.2-Int8） | 事后 |

### 1.4 三个核心疑问

| 疑问 | 答案 |
|---|---|
| **为什么并发不是 32？** | 32 是 vLLM 的软件上限 `--max-num-seqs`（一个 batch 最多 32 个 seq），但真正的瓶颈是**显存 KV cache**。长上下文请求一个就占约 20% 显存，4 个就占到 76%，塞不进第 5 个。所以实际并发 = min(32, 显存能塞下几个)，实际只有 3-4，够不到 32 |
| **为什么又有抢占又有排队？** | 都是"显存不够"的结果，但 vLLM 对每个新请求分别判断：抢一个老请求能立刻腾够显存 → **抢占**；抢了也腾不够、或等一下就有请求跑完 → **排队**。所以同一时刻两者可以并存 |
| **5 分钟那个是事后统计吗？** | 是。它来自 LiteLLM 的 spend logs，只有请求**完成**后才写入。所以 IP 表看到的是"过去 5 分钟已经做完的请求"，看不到"此刻正在跑/排队的是谁" |

### 1.5 为什么"此刻谁在用"看不到

| 数据源 | 有身份(IP/人名)吗 | 时间维度 |
|---|---|---|
| vLLM `/metrics` | ❌ 只有数字，无身份标签 | 实时 |
| LiteLLM spend logs | ✅ 有 api_key → 人名 | 事后（请求完成后） |

两个数据源**对不上**：vLLM 知道"此刻 3 个在跑"但不知道是谁；LiteLLM 知道"谁发过请求"但只有已完成的那批。所以"此刻正在被处理/排队的人"从现有 HTTP 数据源**严格拿不到**，只能靠"过去 30 秒谁发过请求"做概率推断。

## 二、插件状态判断逻辑

数据源两个时间戳：

- **`ll_last`** = LiteLLM 网关记录：该员工最近一次通过网关调用 AI 的时间
- **`audit_last`** = 审计插件上报：该员工机器上的插件最近一次上报事件的时间

判定逻辑（阈值默认 3 小时，`offline_threshold_hours` 可配）：

| LiteLLM 调用 (ll_last) | 插件上报 (audit_last) | 判定状态 | 含义 |
|---|---|---|---|
| 无 | 无 | **未使用** | 没通过网关调用过，也没上报过 = 压根没用 |
| 有 | 无 | **未安装** | 网关有调用记录，但插件没上报 = 装了 Claude 但没装审计插件 |
| 有 | 有（差 ≤ 3h） | **在线** | 网关刚调用，插件也刚上报 = 正在用且插件正常 |
| 有 | 有（差 > 3h） | **离线** | 网关最近有调用，但插件上报停在很久前 = 插件被关/卸载了 |
| 无 | 有 | **未使用** | 插件上报过，但近 24h 没通过网关调用 |

附加判定：

| 附加条件 | 状态 | 含义 |
|---|---|---|
| 该员工 IP 不在白名单内 | **IP异常** (ip_blocked) | 调用来自非白名单 IP，可能账号被挪用 |

## 三、数据源总览

| 数据源 | 地址 | 提供什么 | 访问方式 |
|---|---|---|---|
| vLLM-128 | `192.168.3.128:30080` | 队列/处理中/抢占/KV cache/缓存命中（实时）。**GLM-5.2-Int8 实际路由到此** | HTTP `/metrics` |
| vLLM-129 | `192.168.3.129:30080` | 同上。与 128 是**两个独立实例**（累计 token 差 500 万），LiteLLM 未把 GLM 路由到此，作对比/备用监控 | HTTP `/metrics` |
| LiteLLM | `192.168.3.124:4000` | 请求日志（IP/api_key/耗时，事后）+ key 列表 | HTTP `/spend/logs/v2` + `/key/list` |
| 审计插件上报 | 员工机 → 平台 `/ingest` | 插件事件（时间戳、用户、事件类型） | HTTP POST |
| 组织架构 | `org_structure.csv`（飞书同步） | 员工姓名/部门/邮箱 | 本地文件 |

> **128/129 关系**：实测两者进程启动时间不同、累计 token 差约 500 万，是两个独立 vLLM 实例（非同一实例的两个入口）。LiteLLM 的 `/model/info` 显示 `GLM-5.2-Int8` 只路由到 128；129 可能服务其他模型或作备用。监控页两条曲线分开显示，便于对比。

### 可配置项（页面实时调）

| 配置 | 位置 | 选项 | 说明 |
|---|---|---|---|
| vLLM 采样间隔 | 监控页右上「采样间隔」 | 5s / 10s / 30s / 1min | 改变采集器拉 `/metrics` 的频率；间隔越小曲线越细但开销越大 |
| 图表时间范围 | 监控页右上「图表范围」 | 15分钟 / 1小时 / 6小时 / 1天 | 看实时波动选 15 分钟，看总体趋势选 1 天；大范围自动降采样到 ≤240 点 |
